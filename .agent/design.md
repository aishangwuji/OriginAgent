# 设计约束

以下规则用于规范架构设计决策。新增功能或修复缺陷时，应优先遵循这些边界原则进行开发。

## 核心保持精简，能力向外围扩展

新增功能能力应通过 `channels/`、`tools/`、技能模块或 MCP 服务实现。
`agent/loop.py` 与 `agent/runner.py` 是关键核心流程文件，应尽量少做修改，且每一处修改都要有合理依据。
若某项功能可通过通道适配器、工具或外部 MCP 服务实现，就不应将其内嵌到智能体主循环中。

## 少冗余架构，重智能逻辑

优先选择简洁、易读的代码，而非新增框架层级与间接调用逻辑。
仅在能够切实降低复杂度、保护核心边界、符合项目已有规范范式时，才新增架构分层。
最优解决方案通常是：精简提示词、收紧工具接口约定、仅做通道局部改动，或补充针对性的回归测试。

## 宁可适度重复，不做过早抽象

各个通道和服务提供方允许存在相似逻辑（如重试发送、媒体处理、消息拆分）。
切勿为了消除通道文件间的逻辑重复，强行引入复杂基类或公共辅助工具。
每个通道文件应保持**自包含、可独立阅读**，服务提供方的实现逻辑也遵循同一原则。

## 最小改动，解决实际问题

修复缺陷时，只修改必要代码。
禁止将无关的代码重构、代码清理操作，合并到功能开发或缺陷修复的合并请求（PR）中。
若确实需要重构，应单独提交面向**夜间开发版（nightly）** 的独立合并请求。

## 保证合并请求（PR）易于评审

缺陷修复需明确受保护的不变业务规则，以最小代码改动范围实现规则约束，且仅补充最贴合场景的回归测试。
若代码差异涉及权责边界变更、将业务逻辑改动与代码清理混在一起，需提前拆分提交，避免评审难度过高。

## 显式定义优先隐式魔术

所有配置必须在 `config/schema.py` 的 Pydantic 模型中**显式声明**。
错误处理应主动抛出明确异常，而非静默修正非法入参。
支持服务提供方自动识别，但从工厂类到具体实现类的每一条解析链路，都必须可追溯。

### 术语说明（统一规范）

- PR：合并请求
- MCP servers：MCP 服务
- regression test：回归测试
- premature abstraction：过早抽象
 invariant：业务不变量/约束规则
- Pydantic models：Pydantic 数据模型
- channel adapter：通道适配器
- factory：工厂类
- concrete provider class：具体服务实现类

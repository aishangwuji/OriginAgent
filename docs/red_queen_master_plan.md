# OriginAgent 红后化演进总计划书

Date: 2026-06-08
Status: Proposed
Scope: OriginAgent 持续后台思考、分层感知、世界模型与物理动作能力的长期演进总计划

## 1. 文档目标

这份计划书用于为 OriginAgent 向“红后式智能体”演进提供统一的长期施工依据。

这里的“红后式智能体”不是指一次性实现电影化效果，而是指一个具备以下特征的运行时：

1. 在没有用户显式输入时，仍能持续进行受约束的后台思考。
2. 能接收来自物理世界的感知输入，并将其沉淀为可查询的环境状态。
3. 在需要时可对感知结果做更深层次的复查，而不是只依赖单次粗略理解。
4. 在严格安全、权限、审计和确认机制下，逐步获得对物理设备或机器人的执行能力。

本计划书的目标不是一次性规定所有实现细节，而是统一以下内容：

1. 愿景、边界和非目标。
2. 与现有 OriginAgent 架构相衔接的目标能力地图。
3. 分阶段实施路线与阶段验收标准。
4. 风险、止损和回滚策略。
5. 后续拆分小任务和接力开发时应遵循的规则。

此外，本计划明确包含一条横跨多个阶段的并行基础主线：

1. 连续性与记忆操作系统。

这条主线不属于单一阶段的附属优化，而是后续后台认知、感知、世界模型和动作治理都要共享的基础设施方向。

## 2. 为什么需要单独立项

这条演进路线的改动面很大，横跨以下多个系统边界：

1. 运行时后台调度。
2. 感知输入与多模态理解。
3. 短期环境状态维护。
4. 长期记忆沉淀。
5. 主 Agent 决策方式。
6. 外部设备与机器人控制。
7. 安全、隐私、权限和审计。

如果没有一份稳定的总计划，后续每次开发都容易在局部最优和全局一致性之间反复摇摆，产生以下风险：

1. 把高频感知流错误地塞进现有语义消息通道。
2. 过早接入动作能力，导致安全机制不足。
3. 把短期环境状态和长期事实存储混为一谈。
4. 在尚未定义止损点时贸然铺开多模态和机器人控制。
5. 后续接力开发时，任务边界模糊、依赖不清、回滚困难。

因此，本计划采用“先总计划、再阶段实施、每阶段再拆任务包”的方式推进。

## 3. 现状评估

当前 OriginAgent 已具备若干重要基座，但还没有形成统一的“认知编排层”。

### 3.1 已具备的基座

1. `MessageBus` 已提供轻量的语义消息总线，适合低频文本与内部事件。
2. `ActiveIntentService` 已提供受限的后台主动消息机制。
3. `CronService` 已提供持久化定时任务基础设施。
4. `Dream`、`FactStore`、`NearlineMemoryPipeline` 已提供长期记忆与近线记忆基座。
5. `SafeActionExecutor`、`ActionSafetyGate`、`PermissionResolver`、`ConfirmationManager` 已提供动作安全边界。
6. domain pack 与 device gateway 方向已经为后续物理动作提供了接入形态参考。

### 3.2 当前缺口

1. 缺少统一的后台认知编排层，无法系统性地组织巡检、再规划、提醒、反思和感知结果消费。
2. 缺少专门面向高频感知流的接入层和处理层。
3. 缺少短期环境状态容器，即世界模型。
4. 缺少“粗略感知 + 按需深查”的分层感知策略实现。
5. 缺少连续性与记忆操作系统，无法稳定处理用户身份、作用域、工作记忆、检索融合、上下文组装、晋升和遗忘。
6. 缺少从感知层到动作层的完整治理策略与阶段门禁。

### 3.3 关键现状判断

1. 现有 `MessageBus` 应继续承担“语义总线”职责，不应直接承载高频视频帧、音频块等原始流。
2. `FactStore` 更适合作为长期稳定事实层，不适合直接承载高频瞬时环境状态。
3. 现有主动意图、定时调度和安全执行能力可以复用，但需要一个更高层的统一编排。
4. 现有会话、记忆与摘要能力已经形成连续性交互的雏形，但还缺少统一的身份层、作用域层、工作记忆层和检索构造层，暂时不足以支撑真正长期运行的“无感连续性”。

## 4. 愿景与非目标

### 4.1 愿景

OriginAgent 的长期目标是演进为一个：

1. 可持续后台思考。
2. 可逐步接入视觉、音频和其他传感器。
3. 可维护短期世界模型。
4. 可在安全约束下执行现实动作。
5. 可审计、可解释、可回滚、可逐步增强。

### 4.2 非目标

本计划明确不追求以下目标：

1. 一次性实现完全自主、无限制、自驱动的通用 AGI。
2. 第一阶段就接入完整机器人自治。
3. 把所有感知结果都直接塞进对话上下文。
4. 让大模型对每一帧图片、每一段音频都进行高成本深推理。
5. 为未来可能性过早建设复杂分布式基础设施。

## 5. 总体设计原则

### 5.1 先分层，再增强

先定义清楚语义层、感知层、世界模型层、长期记忆层、动作层，再逐步增强每一层，而不是直接让大模型吞下所有输入。

### 5.2 保持主 Agent Loop 简洁

感知、世界模型和后台认知编排应尽量作为独立服务或 sidecar 流程接入，不要把主循环改成臃肿的全能状态机。

### 5.3 先有保守摘要，再做按需深查

第一层感知只输出高置信、可追溯、成本可控的结构化摘要；需要细节时再回看原始图片、音频或特征数据。

### 5.4 世界模型优先于长上下文注入

Agent 不应靠不断向 prompt 塞场景 JSON 来“记住环境”；应优先通过世界模型和工具查询获取环境状态。

### 5.5 动作能力永远晚于认知能力

必须先证明后台思考、感知、状态维护、冲突检测和安全边界稳定，才允许扩展到真实物理动作。

### 5.6 全程可审计、可回滚

任何主动思考、感知结论晋升、关键告警、深查触发和动作执行都应可追溯其来源、理由、置信度和时间线。

## 6. 目标能力地图

将目标能力拆成六层：

1. 认知编排层：后台巡检、再规划、反思、提醒、异常处理。
2. 感知处理层：传感器输入、事件提取、场景摘要、深度复查。
3. 世界模型层：维护当前空间、对象、人物、状态与时间上下文。
4. 连续性与记忆操作系统层：统一用户身份、作用域、工作记忆、检索融合、上下文构造、晋升与遗忘。
5. 记忆治理层：将值得长期保留的信息沉淀到 `FactStore` 或 nearline memory。
6. 动作执行层：在安全审计下调度设备与机器人动作。

这六层之间的职责边界如下：

1. 感知层负责“看见了什么、听见了什么、当前置信度如何”。
2. 世界模型层负责“当前环境状态是什么、哪些状态已失效、哪些状态发生冲突”。
3. 认知编排层负责“什么值得被关注、什么时候该提醒、什么时候该复查、什么时候该规划动作”。
4. 连续性与记忆操作系统层负责“当前这次推理真正应该看到哪些上下文，这些上下文属于谁，来自哪里，是否可信，何时该被忘记”。
5. 记忆治理层负责“哪些状态应被持久化为长期事实”。
6. 动作执行层负责“如何安全执行外部动作”。

### 6.1 并行基础主线：连续性与记忆操作系统

这条主线用于支撑“长期运行但不失控”的上下文连续性，不应被简化为“多塞一点记忆进 prompt”。

它至少包含以下子模块：

1. 身份层：`user_id`、`household_id`、`device_id`、`session_id` 关系。
2. 作用域层：全局、家庭、用户、设备、会话、任务级别的记忆作用域。
3. 工作记忆层：承载当前任务、当前计划、当前待确认项和当前世界关注点。
4. 检索融合层：融合全文、向量、事实图、世界模型查询结果。
5. 上下文组装层：预算分配、排序、去冲突、最终消息构造。
6. 晋升与遗忘层：决定什么进入长期记忆、什么衰减、什么清除。

该主线的独立设计提纲见：

- [`continuity_memory_os_outline.md`](./continuity_memory_os_outline.md)

## 8. 总线与数据分层策略

### 8.1 语义总线继续保留

现有 `MessageBus` 继续承担：

1. 用户消息。
2. 工具结果。
3. 子代理结果。
4. 主动意图事件。
5. 高价值内部系统事件。

它不直接承载高频原始感知流。

### 8.2 感知层单独建设，但不急于“总线泛滥”

感知层建议采用“统一 ingress + topic 分类”的方案起步，而不是第一天就拆成多个重基础设施的物理总线。

起步阶段可按 topic 逻辑区分：

1. `vision.front_door`
2. `vision.living_room`
3. `audio.living_room`
4. `robot.pose`
5. `sensor.environment`

后续只有在吞吐、隔离或部署需求明确出现时，再演进为多进程或多物理总线。

### 8.3 感知结果必须分层

感知结果至少分为四类对象：

1. 原始记录：图片路径、音频片段路径、采样时间、设备来源。
2. 粗略摘要：`SceneSnapshot`，用于低成本快速理解当前场景。
3. 深查结果：`InspectionResult`，用于对关键快照进行更细节分析。
4. 世界状态：`WorldState`，用于对当前环境提供统一查询。

## 9. 感知模型与数据模型原则

### 9.1 第一层摘要不是“真相”，只是高置信草图

场景摘要应遵循“保守、简洁、带置信度、带来源”的原则。

推荐摘要结构至少包括：

1. `snapshot_id`
2. `timestamp`
3. `source`
4. `image_path` 或 `audio_path`
5. `summary`
6. `objects`
7. `relationships`
8. `confidence`
9. `uncertainties`
10. `provenance`

### 9.2 深查不是“忽略旧摘要”，而是“对旧摘要做核验与补充”

对同一张图片或片段的深查结果应包含：

1. `confirmed`
2. `corrected`
3. `new_details`
4. `uncertain`

这比单纯让模型“忽略已知内容，只补充新细节”更稳妥，因为它允许系统修正第一层摘要中的错误。

### 9.3 世界模型先短期、后长期

世界模型的首要职责是维护短期、可过期、可冲突、可刷新状态，而不是直接替代长期事实存储。

因此：

1. 高频状态先进入世界模型。
2. 只有稳定、高价值、跨时间仍成立的信息才晋升到 `FactStore`。
3. 感知结论默认带过期与置信度衰减。

## 10. 后台认知编排策略

### 10.1 后台思考不等于让大模型持续空转

后台认知循环应优先基于以下触发：

1. 周期巡检。
2. 世界模型变化。
3. 到期提醒。
4. 感知异常。
5. 长期目标需要再规划。
6. 置信度不足，需要深查。

只有当某个问题值得深推理时，才进入更高成本推理。

### 10.2 认知循环的最小职责

最小可用 `CognitiveLoop` 至少应负责：

1. 检查当前是否存在高优先级异常或到期事项。
2. 检查环境变化是否值得发出语义事件。
3. 检查当前目标是否因环境变化而需要再规划。
4. 检查是否有存疑感知需要触发深查。
5. 检查哪些结论值得沉淀进长期记忆。

### 10.3 与现有能力的关系

`CognitiveLoop` 不应替代现有能力，而应编排它们：

1. `ActiveIntentService` 负责发送受限主动跟进。
2. `CronService` 负责定时调度持久任务。
3. `Dream` 负责长期记忆整理。
4. `NearlineMemoryPipeline` 负责近线事件沉淀。
5. `Continuity & Memory OS` 负责把“该轮真正应看到的上下文”构造给 `AgentLoop`。
6. `AgentLoop` 继续作为统一语义执行入口。

## 11. 分阶段实施路线

### Phase 0: 规划与治理基线

目标：
统一术语、边界、阶段目标、风险与任务拆分规则。

必须交付：

1. 本总计划书。
2. 任务包拆分规范。
3. 第一批工作包清单。
4. 连续性与记忆操作系统的独立架构提纲。

明确不做：

1. 真实感知接入。
2. 真实动作执行。

阶段验收：

1. 后续执行任务不再反复讨论总路线。
2. 接力开发者可据此理解边界和优先级。

止损点：

1. 如果方案边界还在频繁摇摆，不进入下一阶段。

本阶段对连续性主线的要求：

1. 明确它是并行基础主线，不是后期收尾优化。
2. 明确它至少需要在 Phase 1 实现最小骨架。

### Phase 1: 后台认知闭环

目标：
在不接入物理感知的前提下，先完成统一后台认知编排层。

必须交付：

1. 最小 `CognitiveLoop` / `CognitiveScheduler`。
2. 与 `ActiveIntentService`、`CronService`、`Dream`、nearline memory 的编排关系。
3. 后台任务预算、频率和去重策略。
4. 可审计的后台认知事件记录。
5. 连续性与记忆操作系统最小骨架：
   - 身份层最小模型
   - 作用域模型最小版
   - 工作记忆最小版
   - `ContextAssembler` v2 最小版

明确不做：

1. 真实摄像头和音频接入。
2. 机器人控制。

阶段验收：

1. 在无用户输入时，系统能周期巡检和受限地主动跟进。
2. 后台认知行为可解释、可限流、可关闭。
3. 上下文构造不再只依赖最近对话和静态记忆拼接，而开始具备显式的工作记忆与作用域治理能力。

止损点：

1. 若后台循环已出现噪音过高、成本过高或行为不可解释，则先收敛这一层，不进入感知阶段。

本阶段对连续性主线的要求：

1. 必须先打好最小骨架，最晚不能晚于 Phase 2 前半段。
2. 如果这一层缺失，后续感知、世界模型和动作归属关系都会产生返工风险。

### Phase 2: 视觉感知原型与分层快照

目标：
建立“粗略摘要 + 原始图片留存 + 按需深查”的最小可用视觉感知链路。

必须交付：

1. 快照采集与存储策略。
2. `SceneSnapshot` 数据模型。
3. 图片路径与摘要绑定。
4. `inspect_snapshot` 深查工具。
5. 最小世界模型查询接口。
6. 连续性主线增强项：
   - 感知快照的身份归属与作用域治理
   - 世界摘要进入上下文构造器的最小接入规则

明确不做：

1. 持续视频流全量实时理解。
2. 多摄像头大规模部署。
3. 真实机器人执行。

阶段验收：

1. Agent 可查询“当前场景摘要”。
2. 对关键场景可回溯到原图做深查。
3. 深查结果可补充或修正第一层摘要。

止损点：

1. 若摘要质量不足以支持后续规划，应先优化数据模型与深查策略，不进入多模态融合阶段。

### Phase 3: 多模态感知与世界模型

目标：
把视觉原型扩展为更稳定的环境状态系统。

必须交付：

1. 音频接入原型。
2. 多源感知融合规则。
3. 世界模型状态更新、过期、冲突和异常检测机制。
4. 感知结论晋升为长期记忆的规则。
5. 连续性主线增强项：
   - 检索融合
   - 晋升与遗忘策略
   - 会话漫游预热或最小预热能力

明确不做：

1. 完整自主机器人导航。
2. 高风险现实动作自动执行。

阶段验收：

1. Agent 能通过世界模型获得比单次快照更稳定的环境判断。
2. 感知冲突和不确定性得到结构化表达。

止损点：

1. 若世界模型无法稳定维护状态，就不允许进入物理动作阶段。

### Phase 4: 动作规划与受控执行

目标：
在现有安全框架基础上，逐步让系统获得物理动作能力。

必须交付：

1. 动作规划入口。
2. 感知到动作的最小闭环。
3. 设备/机器人动作适配层。
4. 额外的安全策略、确认策略和审计策略。

明确不做：

1. 无人监管的高风险自治。
2. 安全边界不明确的动作直通。

阶段验收：

1. 所有现实动作都经权限、确认、审计和回滚设计约束。
2. 任何动作触发都可回溯到其环境依据和规划依据。

止损点：

1. 若现实动作不能做到可熔断、可审计、可人工接管，则不得扩大动作面。

### Phase 5: 稳定化与产品化收口

目标：
对前述能力进行性能、成本、稳定性和治理收口。

必须交付：

1. 观测指标。
2. 故障分级。
3. 数据保留与清理策略。
4. 配置化能力开关和运维说明。
5. 面向长期运行的测试策略。
6. 连续性主线收口项：
   - 预热、漫游、跨端恢复体验
   - 长期记忆膨胀治理
   - 上下文构造质量观测

阶段验收：

1. 系统可长期运行而不过度依赖人工盯守。
2. 后台思考、感知和动作不会在成本或风险上失控。

## 12. 风险清单与止损策略

### 12.1 架构风险

1. 语义总线与感知流混用，造成阻塞和复杂度失控。
2. 世界模型与长期事实存储职责混淆。
3. 背景认知层变成新的“大而全主循环”。

对应策略：

1. 强制分层。
2. 每阶段只引入必要抽象。
3. 先实现 sidecar，再考虑更重的基础设施。

### 12.2 模型风险

1. 场景摘要幻觉。
2. 深查继承错误前提。
3. 高成本模型调用过多。

对应策略：

1. 摘要保守化。
2. 深查返回“确认/纠正/新增/不确定”四类结构。
3. 事件驱动和阈值驱动深查，不做无差别全量深推理。

### 12.3 产品风险

1. 主动行为噪音过高。
2. 用户对后台感知和思考缺乏信任。
3. 权限和隐私表述不清。

对应策略：

1. 默认保守。
2. 强调审计与可关闭。
3. 明确本地存储、保留策略和授权边界。

### 12.4 物理安全风险

1. 误判环境导致错误动作。
2. 动作执行超出授权范围。
3. 无法快速停机或人工接管。

对应策略：

1. 先建认知，再放动作。
2. 动作必须走现有安全闸门并扩展。
3. 所有高风险动作要求人工确认或具备强约束前提。

## 13. 任务拆包与接力开发规范

后续所有执行任务都应拆成独立、可提交、可验证的小任务包。

每个任务包至少包含以下字段：

1. `title`
2. `goal`
3. `scope`
4. `non_goals`
5. `dependencies`
6. `files_or_modules`
7. `acceptance_criteria`
8. `tests`
9. `rollback_plan`
10. `open_questions`

### 13.1 拆包原则

1. 每个任务包尽量只跨一个主模块边界。
2. 每个任务包必须有明确验收标准。
3. 高风险任务必须先有只读/模拟/假实现版本。
4. 任务包之间的依赖关系必须显式记录。
5. 任务包完成后应能独立形成清晰 commit 边界。

### 13.2 接力开发规则

1. 先更新任务包状态，再改代码。
2. 修改前先确认当前阶段目标和边界未漂移。
3. 如果发现阶段前提不成立，应先回到计划层修订，而不是局部硬做。
4. 对高风险任务，先做设计评审或文档评审，再进入实现。

## 15. 里程碑管理建议

建议后续里程碑按“能否独立验证一个新层级”来定义，而不是按“写了多少代码”定义。

推荐里程碑：

1. `M0` 总计划书与拆包规范冻结。
2. `M1` 后台认知闭环可运行。
3. `M2` 视觉分层感知原型可运行。
4. `M3` 世界模型可维护稳定环境状态。
5. `M4` 安全受控的动作闭环可运行。
6. `M5` 长期运行和治理能力达标。

## 16. 当前建议的下一步

在本计划书通过后，下一步不应直接铺开多模块实现，而应先从第一阶段的文档化执行入口开始。

推荐优先顺序：

1. 基于本计划书编写 `RQ-001` 任务包。
2. 基于连续性主线提纲编写 `RQ-002` 与 `RQ-003` 任务包。
3. 明确 `CognitiveLoop` 与现有 `ActiveIntentService` / `CronService` / `Dream` 的关系。
4. 在不接入真实感知设备的前提下，先把后台认知闭环和连续性最小骨架跑通。

这是最稳妥、最容易止损、也最利于后续接力的起点。
